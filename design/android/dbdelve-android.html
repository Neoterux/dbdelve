At 600 dp and wider, the layout is the desktop one. Sidebar, breadcrumbs, editor over grid, and the same secondary- keymap, which reads as Ctrl here. The accessory bar hides as soon as a hardware keyboard connects. An IT person on a tablet with a keyboard should not have to learn a second app.

What stays the same as desktop, on purpose

  • Your SQL runs as typed. The row limit drops rows as they arrive, and the status line says when it did.
  • Connection modes, sql::classify and sql::gate, with every connection starting Read-only.
  • Grid edits appear as SQL before they run, a row is named by its key, and DROP and TRUNCATE are never written.
  • Projects, the palette's scopes, the fuzzy matcher and the themes.

What changes for a phone

  • The sidebar, editor and grid become bottom-nav destinations below 600 dp, and go back to panes above it.
  • An accessory key row brings back Tab, Esc, Ctrl and SQL punctuation.
  • Row editing moves to a sheet. Cells are under a fingertip's 48 dp.
  • Records view handles wide tables in portrait.
  • Going above a connection's mode needs a biometric check, against pocket taps.
  • Passwords move from keyring to Android Keystore, unlocked with the same biometric.

Open problems this mockup doesn't solve

  • GPUI has no Android backend. These screens need a new UI layer. src/db/ could be kept as a Rust core behind JNI or UniFFI under Jetpack Compose, because driver types already stop at that boundary.
  • SSH tunnels shell out to system ssh, which Android doesn't have. They need an in-process SSH library and a new readiness check.
  • The ODBC bridge and plugins don't carry over. Android has no driver manager, so Db2, Oracle and other ODBC-only engines are out.
  • Android kills background apps. A long query needs a foreground service, or it dies when you switch apps.
  • Most production databases aren't reachable from a phone. Without a VPN or a bastion, the Connections list is mostly greyed out. That's the main reason to doubt how much this app gets used.
